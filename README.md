# Проверка договоров поставки — прототип

Локальное веб-приложение для закупщика. Загружаете TXT-файлы (договоры, допсоглашения, письма, проекты) и получаете таблицу: номер договора, поставщик, сумма и срок поставки **на дату проверки**. У каждого значения есть файл, точная цитата и переход к нужной строке исходного текста. Изменённые значения показывают, каким документом они изменены. Несогласованные предложения выведены отдельно. Если данных нет, показывается «нет данных», а неясные ситуации помечены «требует проверки».

> Затрачено времени: **2 ч**.

## Установка и запуск

Нужен только Python 3.10+. Внешних зависимостей нет: используется только стандартная библиотека, ни LLM, ни ключей, ни платных API.

```bash
python run.py
```

Откройте http://127.0.0.1:8000 (порт можно сменить: `python run.py 8080`).

Тесты:

```bash
python -m unittest -v
```

## Как пользоваться

1. Нажмите **«Загрузить TXT…»** и выберите файлы. Файлы можно добавлять по одному, лишние удаляются крестиком. Кнопка **«Демо-файлы»** загружает 6 учебных файлов из `samples/`: они обрабатываются точно так же, как загруженные вручную.
2. Таблица «Условия договоров» показывает значения. Ссылки под значениями открывают исходный текст справа и подсвечивают цитату. Щелчок по строке таблицы раскрывает основания: цитату действующей редакции, исходное значение, несогласованные предложения, «другие суммы» (аванс, лимит) и список связанных документов с их статусом.
3. **Дата проверки** меняется в шапке, и всё пересчитывается.
4. **Вопросы**: четыре кнопки с вопросами из задания или свой вопрос текстом. Вопрос разбирается правилами, а не заранее заготовленными ответами:
   - `Какой срок поставки действует по договору STN-101 на 10 марта 2026 года?` — дата из вопроса («на …») используется как дата расчёта;
   - `Какова сумма договора STN-102?`
   - `По каким договорам поставка раньше 01.04.2026?` — фильтр по сроку плюс несогласованные изменения срока.

Ожидаемые ответы на учебных файлах (на 10.03.2026):

| Вопрос | Ответ |
|---|---|
| Срок STN-101 | 30.04.2026 — изменён подписанным ДС № 1 (было 15.04.2026); проект ДС № 2 (10.05.2026) не согласован |
| Сумма STN-102 | 840 000 ₽ (аванс 252 000 ₽ — не стоимость договора) |
| Сумма STN-103 | нет данных: стоимость определяется приложением № 1, которого нет; лимит 600 000 ₽ — не стоимость |
| Поставка до 01.04.2026 | STN-102 (20.03.2026). Есть несогласованное изменение: письмо поставщика о переносе на 27.03.2026. Также по STN-101 есть неподписанный проект о переносе на 10.05.2026 |

## Известные ограничения

- Только TXT (UTF-8 или Windows-1251). Тип документа определяется по первой строке-заголовку («ДОГОВОР…», «ДОПОЛНИТЕЛЬНОЕ СОГЛАШЕНИЕ… К ДОГОВОРУ…», «ПРОЕКТ…», «ПИСЬМО…» или наличие строки «От:»).
- Статус подписания берётся из строки «Статус:». Подписи на самом деле не проверяются: прототип доверяет тексту.
- Номер договора ищется в заголовке после «№». Связь с другими документами строится по «к договору X» в заголовке или по упоминанию номера в тексте.
- На договор извлекается одна сумма и один срок. Если кандидатов несколько (например, поэтапная поставка), выводится «требует проверки» со всеми кандидатами.
- Правила рассчитаны на деловые формулировки учебного формата. Новые формулировки могут дать «нет данных» или «требует проверки», но не выдуманное значение.
- Вопросы ограничены шаблонами «поле + договор [+ на дату]» и «раньше даты». Это не свободный чат.
- Данные не сохраняются: файлы живут в памяти вкладки браузера, сервер ничего не хранит.

## Записка

**Пользователь.** Специалист по закупкам, который сверяет сумму и срок поставки по пакету документов (договор, ДС, переписка) и должен быстро понять, какое значение действует и откуда оно взято, не перечитывая всё.

**Пять вопросов клиенту перед развитием**
1. Откуда приходят документы и в каком виде: СЭД/ЭДО, почта, сканы? Единый шаблон покупателя или шаблоны контрагентов? Как часто встречаются приложения и спецификации со стоимостью?
2. Что считается источником истины о подписании и вступлении в силу: текст документа, отметка ЭДО, реестр договоров?
3. Какие поля нужны помимо суммы и срока (неустойка, оплата, НДС, этапы поставки, валюта)? Насколько часты поэтапные поставки?
4. Что пользователь делает со статусом «требует проверки»: кто принимает решение, нужно ли фиксировать комментарий и вести журнал?
5. Объёмы, права доступа (подразделения, юристы, внешние пользователи) и куда отдавать результат (Excel, 1С, СЭД)?

**Принятые допущения**
- Условия меняет только ДС, подписанное обеими сторонами, с датой подписания и датой вступления в силу не позже даты проверки. ДС без даты вступления в силу получает «требует проверки» и не применяется. Подписанное, но ещё не вступившее ДС показывается как «не вступило в силу».
- Письма и проекты никогда не меняют условия, они показываются как несогласованные предложения.
- Приоритет определяется датой вступления в силу (затем датой подписания), а не именем файла или порядком загрузки.
- Сумма — это только «стоимость / цена / сумма договора». Аванс, лимит, бюджет и неустойка исключаются. Сумма цифрами сверяется с суммой прописью, при расхождении ставится «требует проверки».
- Срок поставки — дата в предложении о поставке. Даты оплаты, вступления в силу и «по состоянию на» не учитываются. В «перенести с X на Y» берётся Y.
- Если поставщик в ДС не совпадает с договором или документ упоминает несколько договоров, ставится «требует проверки», автоматически ничего не применяется.

**Метрики**
1. *Точность полей на размеченной выборке*: доля верных значений и статусов (значение / нет данных / требует проверки). Отдельно с целевым нулём считается доля «выдуманных» значений, то есть число там, где правильный ответ «нет данных».
2. *Доля значений, принятых закупщиком без исправления*, и время сверки договора до и после внедрения. Измеряется по журналу подтверждений и исправлений (см. улучшение 2).

**Архитектура**

```
Браузер (static/: index.html, app.js)            Python stdlib-сервер (contract_checker/)
 файлы в памяти ──JSON base64──► server.py ──► resolver.analyze(files, дата)
 таблица, основания, просмотр     │              ├─ documents.py  тип, статус, даты подписания/силы, стороны
 исходника с подсветкой цитаты    │              ├─ extractors.py поля: сумма, срок (реестр FIELDS)
                                  │              └─ textutil.py   абзацы, предложения, даты, суммы, числа прописью
                                  └──────────► questions.answer(files, вопрос, дата)  правила разбора вопроса
```

Каждое значение — это кандидат из конкретного предложения со смещениями внутри строки файла, поэтому цитата всегда дословная, а UI подсвечивает ровно её. Resolver связывает документы с договором, классифицирует их (действует / не согласовано / не вступило / требует проверки) и применяет только действующие ДС.

**Три ключевых решения и компромиссы**
1. *Правила вместо LLM.* Плюсы: детерминированно, объяснимо, бесплатно, полностью тестируемо, нет галлюцинаций, и при неудаче получается «нет данных» или «требует проверки», а не выдумка. Минус: хрупкость к нешаблонным формулировкам, и правила нужно поддерживать. Подходит для типовых договоров; для договоров контрагентов понадобится ML/LLM-извлечение с проверкой цитат.
2. *Консервативная политика статусов.* Всё неясное (нет даты силы, чужой поставщик, несколько договоров, расхождение цифр и прописи, несколько значений) не применяется и помечается. Платим большей долей ручной проверки, зато не получаем уверенно неверных значений.
3. *Сервер без состояния, файлы в браузере.* Просто, нет хранения данных и миграций, удобно для демо. Минус: файлы пересылаются при каждом запросе, нет истории и совместной работы, для объёмов не годится.

**100 000 документов и права доступа.** Обработка при загрузке, а не при запросе: очередь, извлечение один раз, результаты и цитаты хранятся в БД (PostgreSQL) с версией экстрактора, тексты лежат в объектном хранилище. Поиск и фильтры идут по индексу (полнотекстовый поиск плюс поля). Связь документов строится по идентификаторам из СЭД или реестра, а не по упоминанию номера. Права проверяются на уровне договора и документа и в фильтрах поиска, чтобы ответ или цитата не раскрывали недоступный документ. Нужен журнал действий. Для нешаблонных документов — LLM-экстрактор, ответ которого принимается только если цитата дословно найдена в исходнике, плюс очередь ручной проверки. Качество мониторится на размеченной выборке.

**Следующие улучшения (по приоритету)**
1. Новые поля — неустойка, условия оплаты, НДС — через реестр `FIELDS` в `extractors.py`, плюс размеченный набор реальных договоров для замера метрики 1.
2. Подтверждение и исправление значения закупщиком с комментарием и журналом, экспорт таблицы в Excel.
3. Опциональный LLM-экстрактор (локальная модель, без платного API) для нешаблонных формулировок: обязательная проверка дословной цитаты и откат на правила.

Как добавить поле (например, неустойку): написать `extract_penalty(doc) -> Extraction` в `contract_checker/extractors.py` по образцу `extract_amount` и зарегистрировать в `FIELDS`. Resolver применит к полю те же правила ДС, писем и проектов, в API появится `fields.penalty`. Затем добавить колонку в `static/app.js` и тесты.

## Отчёт о вайбкодинге

**Инструмент:** Claude Code (модель Claude Opus 5.5) в приложении Claude Desktop: генерация кода, запуск тестов, проверка UI во встроенном браузере.

**Характерные запросы к ИИ**
- «Делаем task/PO_vibecoding_task.docx» — ИИ сам извлёк текст задания из DOCX, изучил 6 файлов, предложил стек (Python stdlib + vanilla JS, правила без LLM) и реализовал ядро.


**Ошибки ИИ и как они найдены**
- Сервер падал при старте на Windows: `UnicodeEncodeError` при выводе русского сообщения в консоль с кодировкой cp1252. Найдено при запуске превью, исправлено выводом ASCII-сообщения.
- Первая версия правила суммы искала только «общая стоимость» и «стоимость поставки». Новый договор с формулировкой «Цена договора составляет…» получил бы «нет данных». Найдено при сверке с требованием «новый договор того же формата»: правило расширено и закреплено тестами `test_other_price_wording` и `test_textual_date`.

**Как проверялась корректность:** 32 автотеста (`tests/`). Они покрывают ответы на 4 вопроса; дословность цитат (цитата сверяется с текстом файла по смещениям); независимость от имён файлов и порядка загрузки; изменение суммы и срока; новый договор; отсутствие значения → «нет данных»; статусы ДС (подписано и действует, не вступило в силу, без даты силы, не подписано, чужой поставщик, ДС к незагруженному договору); расхождение цифр и прописи; конфликт двух сумм. UI проверен вручную во встроенном браузере: загрузка через input, переход к цитате, кнопки вопросов.
